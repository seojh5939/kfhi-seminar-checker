1. 문서 개요
1.1 목적
본 문서는 행사 참석자 관리를 위한 「QR코드 생성기」와 「QR코드 인식기」 2종 Windows 프로그램의 기능·비기능 요구사항을 정의하는 것을 목적으로 한다.
1.2 배경
행사(약 800명 규모) 참석자에 대해 사전에 개인정보가 담긴 QR코드를 발급하고, 행사 현장 각 출입 지점에서 QR코드를 스캔하여 방문(등록) 여부를 확인·기록하기 위함이다.
1.3 범위
	•	QR코드 생성기: 엑셀 명단을 입력받아 암호화된 개인정보를 포함한 QR코드 이미지를 대량 생성
	•	QR코드 인식기: 현장 각 PC에 설치되어 QR코드를 스캔·복호화하고 방문 기록을 로컬에 저장
	•	두 프로그램은 하나의 Git 레포지토리에서 형상관리

3.3 대량 처리 성능 요구사항
	•	목표: 800건 기준, QR 이미지 생성 + 암호화 + 파일 저장 전체 과정이 수 분 내(예: 3분 이내) 완료
	•	암호화(3.4절) 및 이미지 렌더링을 워커 스레드/비동기 큐로 병렬 처리
	•	진행률(Progress Bar)과 처리 건수를 화면에 실시간 표시
	•	생성 중 오류 발생 건은 전체를 중단하지 않고 오류 목록만 별도로 수집하여 종료 후 리포트
3.4 보안 요구사항 — 암·복호화 설계안
3.4.1 검토: SHA-256 단독 사용의 한계
SHA-256은 해시(hash) 함수로 입력을 고정된 길이의 값으로 변환하는 단방향(one-way) 알고리즘이며, 설계상 원문 복원(복호화)이 불가능하다. 인식기가 화면에 성명 등 개인정보를 다시 보여주어야 하므로, 원문을 복원할 수 있는 대칭키 암호화(예: AES) 가 반드시 필요하며, SHA-256/HMAC은 "위변조 여부 검증(무결성 확인)" 용도로 함께 사용하는 것이 적절하다.
3.4.2 제안 설계: AES-256-GCM 대칭키 암호화
아래와 같은 구조를 제안한다.
	•	암호화 대상 원문: 성명, 소속, 직함, 고유일련번호(3.5절)를 JSON으로 직렬화
	•	암호화 방식: AES-256-GCM (대칭키, 인증 태그 내장 — 별도 HMAC 없이도 위변조 탐지 가능)
	•	QR에 담기는 최종 페이로드 = Base64( IV(12byte) + 암호문 + 인증태그(16byte) )
	•	복호화: 인식기가 동일한 대칭키로 IV/암호문/태그를 분리하여 복호화, 인증태그 검증 실패 시 "등록되지 않았습니다" 처리(위변조·손상 QR 차단)
	•	생성기와 인식기는 shared 모듈(2.2절)의 동일한 암복호화 함수를 사용하여 포맷 불일치를 방지
3.4.3 대칭키 관리 방안 비교
QR 생성기는 1대, 인식기는 여러 대에서 동일 키가 필요하므로, 키를 안전하게 배포·보관하는 방법이 핵심 이슈이다. 3가지 옵션을 비교하여 제안한다.
옵션
방식
장점
단점

빌드 시 소스코드에 키를 포함(간단 난독화)
구현이 가장 쉬움, 배포 간편

	•	대칭키는 shared 모듈(2.2절) 내 상수로 관리하며, 소스코드 저장소(Git) 접근 권한을 사내 개발 담당자로 제한하여 키 노출 경로를 관리
	•	빌드 시 키를 코드에 직접 포함(간단 난독화 적용)하며, 별도의 키 파일 배포·설치 절차가 없어 인식기 설치가 간편해짐
	•	추후 보안 요구 수준이 높아지거나(외부 기관 배포 등) 운영 방식이 바뀌는 경우, 3.4.3의 옵션 B/C로 전환 가능하도록 shared 모듈에서 키를 불러오는 인터페이스는 분리하여 설계
※ 하드코딩 방식은 이론적으로 PC에 대한 물리적/코드 접근 권한이 있으면 키가 노출될 수 있다는 한계가 있으나, 위 운영 환경(사내 직원 전용, 내부 행사용)에서는 허용 가능한 수준의 리스크로 판단하여 채택하였습니다.
3.5 QR 식별 및 관리 방안
약 800개의 QR을 생성·인쇄·배포하는 과정에서 관리자가 "이 QR이 누구 것인지" 즉시 식별할 수 있어야 한다. 아래 4가지를 함께 적용할 것을 제안한다.
3.5.1 고유 일련번호(관리번호) 체계 (확정 v1.7)
[확정 v1.7] 일련번호는 QR 생성기가 자동으로 계산하지 않는다. 관리자가 엑셀 등록시트에 "관리번호" 컬럼(3.2절)으로 미리 부여하여 제공하며, QR 생성기는 이 값을 그대로 읽어와 일련번호로 사용한다.
	•	관리번호 채번 규칙(지역 권역 코드 + 순번 등)은 관리자가 자체적으로 관리하며, QR 생성기는 그 규칙의 세부 내용을 알 필요가 없다 — 단순히 엑셀에 적힌 값을 그대로 사용할 뿐이다
	•	형식: 5자리 숫자 (예: 61001). QR 생성기는 형식(자릿수·숫자 여부)과 명단 내 중복 여부만 검증하고, 값 자체의 의미(지역 구분 등)는 해석하지 않는다
	•	일련번호(관리번호)는 QR 암호화 원문(3.4.2절)에도 포함되어, 복호화 후에도 특정 QR을 역추적할 수 있는 키(key) 역할을 한다
※ v1.4~v1.6에서 검토했던 "지역번호 뒷 2자리 + 순번" 채번 로직은 관리자가 엑셀에서 직접 부여하는 방식으로 결정되어, QR 생성기가 별도로 구현할 필요가 없어졌다. 관련 채번 규칙(권역 코드표 등)은 참고용으로 남겨두되, 시스템 구현 요구사항에서는 제외한다.
3.5.2 파일명 규칙 (확정 v1.4)
[확정] QR 이미지 파일명은 일련번호 5자리 그대로 사용한다 (소속·직함·성명은 파일명에 포함하지 않음).
	•	예: 61001.png
	•	소속(지역) 단위로 하위 폴더를 자동 분류하여 저장 (예: /output/광주북부후원이사회/61001.png)
	•	파일명만으로는 사람이 누구인지 알 수 없으므로, 3.5.3절의 매니페스트 CSV(일련번호 ↔ 성명·소속·직함 매핑)를 반드시 함께 사용하여 식별한다

3.5.4 배포 형태 (확정)
[확정] QR은 별도 인쇄 레이아웃 없이 이미지 파일(PNG)로만 배포한다. 명찰 디자인은 별도로 이미 제작 중이며, 완성된 명찰 디자인에 QR 이미지만 삽입하여 사용하는 방식이다. 따라서 QR 생성기는 아래 두 가지에 집중한다.
	•	QR 이미지를 명찰 디자인에 삽입하기 용이하도록 여백 없는 정사각형 PNG(투명 또는 흰색 배경)로 출력
	•	3.5.2 파일명 규칙에 따라 소속별 폴더에 저장하여, 명찰 디자인 작업자가 각 이미지를 빠르게 찾아 매칭할 수 있도록 지원
※ 별도 인쇄용 프리뷰 시트나 명찰형 출력 옵션(GEN-07)은 본 버전에서 제외한다. 대신 3.5.3의 매니페스트 CSV(성명·소속·직함·파일명 매핑)를 명찰 디자인 작업 시 참조 자료로 활용한다.

	•	프로그램을 처음 실행하면 "이 PC가 설치된 장소명"을 입력받는 화면을 표시 (예: "메인홀 입구" 입력 후 저장)
	•	입력된 장소명은 로컬에 저장되며, 이후 실행 시에는 저장된 장소명이 자동으로 표시되고 이 등록 화면을 다시 거치지 않음
	•	메인 화면에는 현재 등록된 장소명을 확인 표시하고, [시작하기] 버튼 클릭 시 Step2(QR 스캔 화면)로 이동 (별도의 장소 선택 드롭다운은 두지 않음)
4.2.1 장소 변경 절차
[확정] 이미 등록된 장소를 다른 장소로 변경해야 하는 경우, 데이터 유실을 막기 위해 아래 절차를 강제한다.
	•	설정 화면(4.5절 SET-04)에서 "장소 변경" 메뉴 진입
	•	변경 시도 시 "현재 등록된 장소({장소명})의 방문기록을 먼저 다운로드해 주세요"라는 안내 문구와 함께 CSV 다운로드 버튼을 표시
	•	방문기록 CSV 다운로드를 완료해야 새 장소명 입력 화면으로 진행 가능 (다운로드 전에는 장소명 변경 비활성화)
	•	장소명 변경 후에도 기존 로컬 DB의 방문기록 자체는 삭제하지 않고 보존하며, 변경 시점 이후의 신규 방문기록부터 새 장소명으로 저장
※ 이 절차는 스탭이 실수로 장소명을 바꿔 이전 방문기록을 못 찾는 상황(데이터 유실로 오인)을 방지하기 위한 것으로, 다운로드를 강제하는 확인 절차와 안내 문구가 UI상에 명확히 노출되어야 합니다.

	•	최초 방문/재방문 여부는 QR 내 고유일련번호(3.5.1절)를 기준으로, 해당 인식기(장소)에서 이전에 동일 일련번호가 스캔된 이력이 있는지로 판별

v1.0에서 제기되었던 8건의 논의사항에 대해 관리자와 협의하여 아래와 같이 확정하였다. 각 항목의 세부 내용은 해당 절을 참조한다.

✔ 암호화 키 배포 방식 → 내부(사내) 전용 프로그램이므로 옵션 A(하드코딩) 채택 (3.4.3절)

✔ 설치/업데이트 배포 방식 → 생성기·인식기 각각 별도 설치 파일 제공. 업데이트도 설치파일 배포 후 개별 다운로드·설치 방식 (5장)
6.2 v1.1 → v1.2 확정 내역 (수집 항목 축소)
관리자 요청에 따라 QR 생성·인식에 사용하는 개인정보 항목을 성명, 소속, 직함 3개로 축소하였다. 전화번호, 직분, 소속교회를 삭제함에 따라 영향을 받는 전 영역(입력 화면, 암호화 페이로드, 매니페스트, 저장 데이터, 화면 문구 로직)을 함께 수정하였다.
✔ 전화번호/직분/소속교회 삭제 여부 → 3개 항목 전체 삭제 확정. 이후 성명·소속·직함 3개 항목만 수집·암호화·저장 (3.2, 3.4.2, 3.5.3, 4.4절)
✔ 직분 삭제에 따른 인식 성공 호칭 로직 → 직함을 호칭으로 사용하며(직함+"님"), 이사회 소속 사모 참석자를 위해 직함 목록에 "사모" 항목을 신규 추가 (4.3.1절)
※ [확정 v1.3] 전화번호 삭제로 인해 3.1절 GEN-02(입력값 검증)의 전화번호 형식 검사 항목도 함께 제거하였습니다. 참석자 본인 확인이나 사후 연락이 필요한 경우, 관리자가 별도로 보유·관리하는 스프레드시트에서 전화번호를 조회할 수 있으므로 본 시스템(QR 생성기/인식기)에서는 전화번호를 재수집하지 않는다.
6.3 v1.2 → v1.3 확정 내역
✔ 전화번호 미수집에 따른 본인 확인·연락 수단 → 관리자가 별도로 보유한 스프레드시트에서 전화번호를 조회 가능하므로, 본 시스템은 전화번호를 재수집하지 않는 것으로 확정 (2.1절 참고, 별도 연동 불필요)
6.4 v1.3 → v1.4 확정 내역 (일련번호·파일명 규칙)
✔ 일련번호 체계 → "지역번호 뒷 2자리 + 순번 3자리"(총 5자리)로 확정. 서울은 예외적으로 20 사용 (예: 광주북부후원이사회·이사·정현택 → 61001) (3.5.1절)
✔ QR 이미지 파일명 규칙 → 소속·직함·성명을 파일명에 포함하지 않고, 일련번호 5자리를 그대로 파일명으로 사용 (예: 61001.png) (3.5.2절)
6.5 v1.4 → v1.5 확정 내역 (지역번호 매핑 기준 정정)
✔ 지역번호 매핑 기준 → 후원이사회 명칭이 아니라 실제 관할 지역의 전화 지역번호를 기준으로 함을 확인. 예: 광주북부후원이사회는 명칭과 달리 관할 지역이 전남이므로 지역번호 061의 뒤 2자리 "61"을 사용 (3.5.1절)
6.6 v1.5 → v1.6 확정 내역 (지역번호의 상위 개념 명확화)
지역번호는 개별 후원이사회 단위가 아니라, 시/도 단위의 "권역" 기준으로 부여되는 상위 개념임을 확인하였다. 즉 하나의 권역(예: 전남)에 속한 여러 후원이사회(광주북부, 광주남부 등)는 모두 같은 지역번호를 공유하며 순번으로만 구분된다.
✔ 지역번호 부여 단위 → 개별 후원이사회가 아닌 시/도 권역 단위로 지역번호 부여. 같은 권역에 속한 여러 후원이사회는 지역번호를 공유하고 순번을 이어서 채번 (3.5.1절)
✔ 동일 권역 내 복수 후원이사회의 순번 채번 방식 → 권역(지역번호) 단위로 순번을 연속 채번하는 것으로 확정 — v1.4에서 가정했던 방식이 최종 확정됨 (3.5.1절)
6.7 v1.6 → v1.7 확정 내역 (관리번호 외부 제공 방식으로 전환)
일련번호(관리번호) 채번을 QR 생성기가 직접 계산하지 않고, 관리자가 엑셀 등록시트에서 미리 부여해 제공하는 방식으로 최종 확정하였다. 이에 따라 v1.4~v1.6에서 검토한 "지역번호 뒷 2자리+순번" 자동 채번 로직과 16개 권역 코드표는 시스템 구현 범위에서 제외한다.
✔ 일련번호(관리번호) 산출 주체 → QR 생성기가 아닌 관리자가 엑셀 등록시트의 "관리번호" 컬럼으로 사전 제공. 생성기는 형식·중복 검증만 수행하고 그대로 사용 (3.2, 3.5.1절)
✔ 지역 권역 코드표 확인 필요 여부 → 관리번호를 외부에서 제공받으므로 더 이상 필요 없음 — 이전 6.4~6.6절의 관련 확인 필요 항목은 해소됨
